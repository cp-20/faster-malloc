1. 背景：そもそもなぜ malloc / free は難しいのか？

プログラムがメモリを必要とするとき、OS カーネルは mmap や brk といったシステムコールで仮想メモリを貸し出してくれます。 しかし、アプリケーションが malloc(32) や free(p) を呼ぶたびに OS へお願いしていては、システムコール 1 回あたり数千ナノ秒かかり、プログラムはまったく動きません。

そこでユーザー空間の「メモリアロケータ（malloc）」が OS から大きな塊をまとめて借り、アプリに小分けにして貸し出します。このとき、互いに相反する 5 つの課題を同時に解く必要があります。

① 速度（CPU 命令数と分岐）

  • Web サーバやコンパイラ、インタプリタでは全実行時間の数%〜数十%を malloc/free が占めます。
  • 高速パス（Fast Path）は数命令〜十数命令で終わらせ、ロックやシステムコールを絶対に避ける必要があります。

② マルチスレッド競合（Contention）

  • 1 つのグローバルな空きリストを Mutex で守ると、コア数が増えるほどロック待ちで性能が崩壊します。
  • かといってスレッドごとにメモリを溜め込みすぎると、メモリ使用量（RSS）がスレッド数倍に膨れ上がります。

③ 断片化（Fragmentation）

  • 内部断片化：33 B 欲しいのに 64 B 渡すと 31 B が無駄になる。
  • 外部断片化：空き領域の合計は十分あるのに、細切れで連続しておらず大きな要求に応えられない／OS へ返却できない。

④ キャッシュ局所性（Locality）

  • 命令数が少なくても、割り当てたメモリが物理ページあちこちに散らばると L1/L2 キャッシュミスが多発し、実測の壁時計時間（Wall Clock）が遅くなります。
  • 直前に解放した「暖かい（warm）メモリ」を再利用できるかが鍵です。
⑤ OS へのメモリ返却（RSS 管理）とのジレンマ：
解放されたメモリをアロケータが手元にキャッシュすれば次の malloc は爆速になりますが、OS に返さないためプロセスがメモリを食いつぶします。逆にすぐ返却（munmap / MADV_DONTNEED）すると、再確保時にページフォールト（カーネルによるゼロ埋め）が発生して遅くなります。

2. faster-malloc の狙いと 3 つの実装

このリポジトリでは、既存の jemalloc・tcmalloc・mimalloc や学術論文（Free-list shaping、JIT 値特殊化など）の知見を踏まえ、 ゼロから 3 つの LD_PRELOAD 互換アロケータを構築・計測しています。

v1 (libfastmalloc.so)

ベースライン

  • テーブル引きのサイズクラス分類
  • スレッドごとのフリーリスト
  • スピンロック保護の Central リスト
  • v2 の改善効果を測定するための基準

v2 (libfastmalloc2.so)

現在の主力・最速

  • 1024 B 以下は算術シフトのみ
  • 64 KiB スパン（ブロックヘッダ 0 B）
  • 並列 TLS 配列＋フレームレス高速パス
  • O(1) バッチ転送＋Census ページパージ

JIT (libjitmalloc.so)

実験的・動的特殊化

  • 1/64 サンプリングでホットサイズを計測
  • 上位クラス専用の機械語を動的生成
  • TLS オフセットを即値に埋め込み
  • 負荷変化を検知して再 JIT

4. サイズクラス分類（fm_class_of）：分岐とメモリアクセスの削減

v2 は SMALL_MAX = 32,768 B (32 KiB) 以下の割り当てを 145 段階のサイズクラス（0..144） に丸めます（[size_classes2.h](file:///home/cp20/ghq/github.com/cp-20/faster-malloc/src/size_classes2.h)）。

  • 1024 B 以下（Class 0〜64）は「算術計算のみ」：(size + 15) >> 4 のビットシフトだけでクラスが決まります。16 B 刻みで、テーブル参照（メモリアクセス）が一切発生しません。
  • 1025 B 〜 32 KiB（Class 65〜144）は「1 バイトテーブル」：kClassBig[(size + 15) >> 4] を参照します。サイズが大きくなるほど刻み幅（64B → 128B → 256B → 512B → 1024B）が粗くなり、クラス数を 145 個に抑えています。
  • 32 KiB 超は LARGE_CLASS：スパンには入れず、専用の Large パス（mmap ＋ Large キャッシュ）へ流します。

5. 64 KiB スパンと「ブロックヘッダなし」の設計

free(p) が呼ばれたとき、アロケータは「ポインタ p がどのサイズクラスのブロックか」を知る必要があります。 v2 では 64 KiB（SPAN_SIZE = 65536）境界に揃えた「スパン（Span）」 を使い、各ブロックの直前にヘッダを一切置きません。

  • 1 スパン = 1 サイズクラス：スパン内の全ブロックは同じサイズです。
  • 先頭 64 バイトだけがメタデータ（FM_Span）：残りの空間にブロックが隙間なく並びます。
  • O(1) 逆引き：p の下位 16 ビットを切り捨てる（p & ~0xFFFF）だけで即座にスパン先頭の FM_Span に到達し、sp->cls を 1 回のロードで読めます。
  • 初回スパンの小型化（ADR 0060）：滅多に使われないクラスでいきなり 64 KiB 確保して RSS を増やさないよう、各クラスの最初のスパンだけは最小限のサイズ（約 16 KiB 強）で確保します。
図2: 64 KiB アラインスパンと free() 時のビットマスク逆引きアニメーション

6. 並列 TLS 配列とフレームレス高速パス（ここが 7 倍速の正体）

開発ログ（README.md）によると、スレッドローカルデータの持ち方を変えただけでベンチマークが 144 ns/op → 22 ns/op（約 7 倍） へ跳ね上がりました。理由は 3 つあります。

① 構造体配列 (AoS) ではなく並列配列 (SoA)

struct Bin { void *head, *tail; uint32_t cnt; } bins[145]; にすると 1 要素が 24〜32 B になり、インデックス計算にシフトや加算命令が必要です。

v2 は 8 B ポインタの並列配列にしました：

__thread void *fm_head[145];
__thread void *fm_tail[145];
__thread uint32_t fm_cnt[145];

これにより x86-64 では mov %fs:(%rdx,%rcx,8), %rax の単一命令でリスト先頭を引けます。

② noinline によるフレームレス高速パス

  • fm_refill_class や fm_flush_bin などの遅いパスを __attribute__((noinline)) で完全分離。
  • その結果、malloc / free の高速パスは関数プロローグ（スタック確保・レジスタ退避）が不要な「フレームレス関数」になり、全工程が約 13 命令に収まります。

③ 起動時 GOT→即値バイナリパッチ

共有ライブラリ（.so）の TLS 参照は通常 GOT（Global Offset Table）を 1 回ロードしますが、fm_tls_patch_ctor が起動時に自身の機械語を走査して即値オフセットへ書き換え、メモリアクセスをさらに 1 回削ります。

7. バッチ転送・Central スタック・Bump カービング

ローカル TLS キャッシュが空になったり（fm_head[cls] == NULL）、解放が溜まって上限（kClassLimit[cls]、小サイズで 256 個・大サイズで 4 個）に達したときは、 全スレッド共有の Central スタック（fm_central[cls]） と バッチ（FM_Batch）単位で O(1) やり取り します。

  • Flush 時はリストを辿らない：他のスレッドから解放されたブロックが混ざったリストはメモリ上に散らばっており、辿ると L1/L2 キャッシュミスが多発します（ADR 0014 で検証）。そのため v2 は fm_head..fm_tail の塊をリンクを辿らず O(1) で Central へ渡します（同一スパン由来と分かっている場合のみカウント）。
  • Refill 時の Bump カービング：Central も空のときは、スパンの未切り出し領域（fm_bump_ptr .. fm_bump_end）または新規 mmap スパンから kClassLimit[cls] 個だけ切り出してローカルへ持ち、残りのブロック群は「スパン純粋（FM_COUNT_PURE）」なバッチとして Central へ公開します。

8. メモリ返却（Census / ページパージ）と大規模キャッシュ

初期の v2 は「速いがメモリを OS に返さない（RSS が高い）」という弱点がありました。これを Round 2〜6 の改良で解消しています。

① 自動スパン回収 (Census)

一定回数の Flush ごとに Central 内のバッチをスパン単位で集計（trylock で競合を回避）。全ブロックが空きになり dead_mark の寿命を超えたスパンは munmap で OS へ返却します。

② ページ粒度パージ (ADR 0030)

1 個でも使用中ブロックが残っているとスパン全体は munmap できませんが、完全に空いている 4 KiB ページを検出して MADV_DONTNEED で物理メモリを解放します（purged_mask で管理）。

③ Large パス & 64 MiB キャッシュ

32 KiB 超は 1 回の mmap で確保（余白トリム用の munmap 2 回を省略）。解放時は 48 バケット・最大 64 MiB のスレッドローカルキャッシュに保持し、ホットウィンドウ外の不要ブロックは即 munmap します。

9. JIT 版（libjitmalloc.so）の動的特殊化と限界

libjitmalloc.so は実行中にアプリのサイズ分布を学習し、malloc のエントリポイントを機械語レベルで書き換えます。

  • 仕組み：64 回に 1 回のサンプリングでヒストグラムを作り、集中度が高い上位 4 クラスについて、サイズ比較分岐と「%fs:(固定オフセット)」を埋め込んだコードを jit_stubs.S テンプレートから生成し、関数ポインタをアトミックに差し替えます。
  • なぜ静的 v2 に負けるのか？：特定の 1 サイズだけを連打するケースでは数%速くなりますが、複数のサイズ比較（レンジチェック）が増えると分岐コストがかさみ、「最初から算術シフトで一発計算＋インライン展開」できる静的 v2 の方が汎用的に速いという結果になりました。

10. 他のアルゴリズム ①：古典・基礎アルゴリズム

アロケータの進化を理解するための 4 つの基礎方式です。タブを切り替えて構造を確認できます。

Bump Allocator（Arena / Region-based）

大きな連続メモリの現在位置ポインタを ptr += size と進めるだけ。個別 free(p) はできず、処理の終わりに Arena 全体を一括解放します。

  • メリット：数命令で完了する究極の高速性。外部・内部断片化がほぼゼロ。
  • デメリット：長寿命オブジェクトと短寿命オブジェクトが混ざると解放できない。
  • 使われる場所：ゲームエンジンのフレーム一時領域、コンパイラの AST、v2 内部の新規スパン切り出し。

Free List + Boundary Tags（First-Fit / Best-Fit）

dlmalloc の基礎となった古典方式。空きブロックを双方向リストで管理し、各ブロックの前後にサイズタグ（Boundary Tag）を置きます。解放時に隣接ブロックが空いていれば結合（Coalescing）して大きな空きに戻します。

  • メリット：任意のサイズを細かく扱え、結合により外部断片化に強い。
  • デメリット：リスト探索が線形時間になり得る。全ブロックにヘッダが必要で、マルチスレッド時のロック競合が起きやすい。

Buddy System（バディシステム）

メモリを 2 のべき乗（4 KiB, 8 KiB, 16 KiB…）単位で半分ずつ分割して貸し出し、解放時はアドレスの 1 ビット反転（XOR）で求まる「相方（Buddy）」も空いていれば即座に結合して元のサイズに戻します。

  • メリット：結合判定が O(1) と高速で、ページ単位の連続領域確保に強い（Linux カーネルのページアロケータ）。
  • デメリット：2 のべき乗への丸めにより最大約 50% の内部断片化が起きるため、数バイト〜数百バイトの汎用 malloc には向きません。

Slab / SLUB Allocator

同じサイズ・同じ型のオブジェクト専用のキャッシュ（Slab）をページ単位で用意し、空きスロットをフリーリストで管理する方式（Linux カーネルのオブジェクト管理）。

  • メリット：同一サイズオブジェクトの連続確保・解放が爆速で、断片化が極めて小さい。
  • 現代アロケータへの継承：サイズクラスごとの専用スパン／ページを使う tcmalloc・jemalloc・mimalloc・faster-malloc v2 は、Slab の汎用化といえます。

11. 他のアルゴリズム ②：現代の主要汎用アロケータ

glibc ptmalloc2

Linux 標準

  • 構造：dlmalloc をマルチスレッド対応させたもの。複数の Arena とスレッドごとの tcache を持つ。
  • 特徴：各ブロック直前に 8〜16 B のヘッダを持つ。Fastbin / Unsorted / Small / Large など多数のビンを条件分岐で使い分けるため、高速パスでも命令数が多い。

Google tcmalloc

Thread / Per-CPU Cache

  • 構造：スレッド（または CPU コア）ごとのキャッシュ ＋ Central Free List ＋ PageHeap。
  • 特徴：PageMap（基数木）でポインタからスパンを引く。faster-malloc v2 と発想は近いが、v2 は 64 KiB アラインマスクで PageMap 参照すら省き、高速パスをさらに軽量化している。

jemalloc

低断片化・長期稼働向け

  • 構造：複数 Arena ＋ Extent（チャンク）＋ ビットマップ管理 ＋ tcache。
  • 特徴：低い仮想アドレスを優先再利用することで、長時間動くサーバやブラウザでのメモリ断片化（RSS 増大）を非常に低く抑える。

Microsoft mimalloc

高局所性・Cross-free 最強

  • 構造：64 KiB ページを束ねたセグメント上で、フリーリストを 3 種類に分割（Free-list sharding）。
  • 特徴：別スレッドが解放したブロックを CAS で元のページへ戻し、同じ暖かいページを使い続けるためキャッシュ局所性と Cross-thread free が極めて優秀。

12. ベンチマーク ①：実行命令数（Callgrind）の厳密比較

実測時間（Wall Clock）は仮想環境や CPU 周波数変動で ±10% 揺れますが、Callgrind による総実行命令数（Ir）は 1 命令の狂いもなく再現します（[docs/results.md](file:///home/cp20/ghq/github.com/cp-20/faster-malloc/docs/results.md) の実測データ）。 ワークロードを切り替えて各アロケータの命令数（小さいほど高速）を比較できます。

ベンチマークから読み取れる事実：
v2 は測定された全 7 種のマイクロワークロードすべてで glibc・tcmalloc・jemalloc・mimalloc より少ない命令数を記録しています（glibc 比 57〜64% 削減）。

弱点と Round 2〜6 での改善（正直な評価）

  • RSS（メモリ消費量）：espresso ではスレッドキャッシュ分だけ RSS が glibc (3.4 MB) より大きい 9.0 MB になります。一方、bursty アイドル時 RSS はページ粒度パージ（ADR 0030）により 88 MB → 44 MB まで削減され、mimalloc（55 MB）を上回る最小値に達しました。
