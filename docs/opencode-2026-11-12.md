# Work log — macro benchmarks & optimisation, 2026-11-12

Branch: `opencode/macro-bench-optimization`. Design/experiment
decisions are recorded as ADRs in [docs/adr/](adr/README.md); this log
holds the numbers.

Environment note: the development VM is shared and CPU-capped
(~1.5 shared CPUs, 6 GB RAM). Wall-clock runs here show CPU-throttling
episodes that can inflate a whole scenario batch by ~10–100× (one
baseline batch measured calloc at 9203 ns/op; the interleaved re-run
says ~70). All numbers below are therefore min-of-N with allocators
interleaved round-by-round, and anomalous batches were re-measured
before being believed. No valgrind/perf on this VM; tcmalloc/jemalloc/
mimalloc are not installed, so comparisons are glibc / v1 / v2 / jit.

OpenCode note: the free models under the `opencode/` provider were
tried first, as instructed. `opencode/deepseek-v4.1-flash-free`
immediately returned "Free usage limit reached", and
`opencode/big-pickle` did not answer a trivial prompt within 100 s
(and left an orphaned server process). The coding below was therefore
done directly; OpenCode reliability on the free tier is a blocker to
report, not a tool that contributed.

## Phase 1 — Baseline (existing suite, unmodified code)

Correctness: `test_basic` PASS and `bench/stress` PASS under glibc,
v1, v2, jit.

Existing suite, wall clock ns/op, min of 5 (`bench/micro`, `bench/mt`):

| scenario | glibc | v1 | v2 | jit |
|---|---|---|---|---|
| churn 8 B | 10.43 | 7.70 | **5.42** | 8.12 |
| churn 64 B | 10.59 | 8.23 | **5.44** | 8.11 |
| churn 1 KiB | 10.77 | 11.56 | **6.82** | 7.69 |
| batch 64 B | 20.99 | 16.59 | **10.33** | 11.62 |
| rand | 156.3 | 119.5 | 67.1 | **66.7** |
| pareto 50k×10 | **~1400** | ~1850 | ~3000 | ~3050 |
| hold | 21.80 | 18.68 | **12.76** | 14.10 |
| threads | 11.14 | 7.76 | **5.47** | 8.13 |
| large 64 KiB | **28** | ~6100 | ~9000 | ~9000 |
| realloc | 4.81 | **3.33** | 3.76 | 3.74 |
| calloc 4 KiB | ~88 | — | **~70** | — |
| touch | 27.07 | 20.87 | **6.71** | 9.85 |
| mt local (s) | 0.017 | 0.017 | 0.016 | 0.016 |
| mt cross (s) | 0.164 | 0.050 | **0.045** | 0.052 |

Findings:

1. **`large` is a genuine ~300× gap** (v2 ~9000 ns/op vs glibc 28),
   reproduced across interleaved rounds: every large allocation is an
   mmap (+trim) and every free an munmap, plus first-touch faults.
   → ADR 0011 (large-block cache).
2. **`pareto` is a genuine ~2.1× gap** (v2 ~3000 vs glibc ~1400).
   The distribution reaches 512 KiB; ~20 % of allocations are ≥ 64 KiB
   and dominate the time through the same mmap/munmap path. The large
   cache should recover most of it.
3. **calloc is *not* a gap**: the first batch's 9203 ns/op was a
   throttling artefact; interleaved, v2 (~70) beats glibc (~88).
   → ADR 0012 deferred with evidence.

## Phase 2 — Macro benchmarks (`bench/macro.c`, runner `bench/macro.sh`)

Five scenarios modelling real programs (deterministic seeds, one JSON
line each, ops = allocation operations):

- `server` — multithreaded request server (larson-like): 4 threads,
  per-request header + 1–3 payload buffers (64 B–2 KiB), 5 % long-lived
  sessions, ~25 % of payload frees handed to another thread through a
  bounded MPMC queue.
- `compiler` — build a ~4k-node tree per translation unit (node sizes
  48–192 B, interned-name strings, attribute blocks), walk it, tear it
  down in bulk; 600 units.
- `jsondoc` — build object/array/string/number trees, serialise into a
  realloc-grown buffer, retain every 16th document in a 64-slot cache
  with eviction; 6000 documents.
- `kvstore` — chained hash table, zipf-ish keys over 30k key space,
  insert/update(realloc)/delete/lookup churn, table growth by
  rehashing into calloc'd arrays; 2M operations.
- `game` — 15000 frames; per frame 400–800 transient allocations freed
  in bulk at frame end, plus a persistent entity pool with
  spawn/despawn churn and an update walk.

Development note (trial and error belongs in the record): the first
version of the server scenario's transfer queue was a hand-rolled
claim-counter ring. It double-freed under load — under **glibc
itself** (tcache/fastbin corruption aborts at 8 threads × 300k) — and
passed with the transfer disabled, which isolated the bug to the
benchmark, not the allocators. The queue was replaced with Vyukov's
bounded MPMC queue (per-slot sequence numbers); the scenario now runs
clean under glibc, v1, v2 and jit, and ASan-clean. The README's own
history (§6) records the same lesson: three development bugs were in
the measurement harness, not the allocator.

Macro baseline (unmodified allocators, min of 3, interleaved; ns/op,
peak RSS in KiB):

| scenario | glibc | v1 | v2 | jit | v2 RSS |
|---|---|---|---|---|---|
| server | 236.1 | **140.6** | 196.9 | 220.5 | 10756 |
| compiler | 74.4 | 50.5 | **35.9** | 36.7 | 4444 |
| jsondoc | 136.4 | 109.1 | **103.4** | 106.6 | 4932 |
| kvstore | 596.1 | 491.4 | 492.5 | 489.9 | 6672 |
| game | 75.9 | 25.2 | **21.5** | 23.1 | 3724 |

Readings:

- v2 beats glibc everywhere on macro workloads (1.2–3.5×), and leads
  compiler/jsondoc/game outright.
- **`server` looked like a v2 loss against v1** (196.9 vs 140.6).
  Investigated in Phase 3 / ADR 0013: it was measurement noise
  (rankings inverted between batches; the benchmark's teardown was
  inside the timed region and has been fixed). At 2 threads v1 ≈ v2,
  both well ahead of glibc.
- kvstore is dominated by hashing/pointer chasing (~490 ns/op for
  every allocator); allocator differences wash out, as they should in
  a real program.
- v2's peak RSS is the highest or near-highest in every row (spans
  and caches are never returned) — the known gap in ADR 0010.

## Phase 3 — Optimisation

### Experiment 1: large-block cache + untrimmed large mappings (ADR 0011) — KEPT

Changes, all in `src/fm_core.h` (+ wrapper fixes in `fm_static.c`,
`fm_jit.c`):

1. Freed large blocks are cached per thread in power-of-two size
   buckets (intrusive lists through a new span-header field) with a
   4 GiB per-thread cap on retained *virtual* bytes; `malloc_trim`
   drains the cache.
2. Large allocations use a new untrimmed mapping (`fm_map_large`):
   one mmap, header at the 64 KiB-aligned base inside it, raw mapping
   recorded in the header, one munmap at free — 2 syscalls per
   alloc/free pair instead of 4.
3. calloc distinguishes fresh mappings (zero) from cache hits
   (stale) via an out-parameter and memsets only the latter.
4. A first version of (2) had a real bug: the reuse fit-check counted
   the head slack as usable space and could hand out a block up to
   ~64 KiB too small. `bench/stress` under the FM_DEBUG invariant
   checks caught it; fixed by fitting/bucketing on usable length
   (`fm_large_usable`). Full story in ADR 0011.

Results (ns/op, interleaved min-of-N; baseline → after):

| scenario | glibc | v2 before | v2 after |
|---|---|---|---|
| large 64 KiB | 27.6 | ~9000 | **9.4** |
| pareto | ~1235–1400 | ~3000 | **914** |
| churn 8/64/1 KiB | 10.5/10.6/10.7 | 5.4/5.4/6.8 | 5.4/5.5/6.9 |
| batch 64 B | 20.8 | 10.3 | 10.2 |
| rand | 147.4 | 67.1 | 65.3 |
| hold | 21.9 | 12.8 | 12.7 |
| threads | 11.2 | 5.5 | 5.5 |
| realloc | 4.8 | 3.8 | 3.8 |
| touch | 27.0 | 6.7 | 6.3 |
| mt local / cross (s) | 0.018/0.213 | 0.016/0.045 | 0.020/0.065 |

No existing-suite regressions (mt figures are at the noise floor of
this host). Macro suite after (server used the old timing here; see
the investigation below):

| scenario | glibc | v1 | v2 before | v2 after | jit |
|---|---|---|---|---|---|
| compiler | 76.3 | 53.1 | 35.9 | 37.0 | 36.7 |
| jsondoc | 135.9 | 110.3 | 103.4 | 103.6 | 107.6 |
| kvstore | 601.9 | 514.5 | 492.5 | 514.7 | 503.0 |
| game | 75.6 | 25.2 | 21.5 | 21.5 | 23.2 |

(kvstore moved with the whole batch, glibc included; relative
positions unchanged. The large path does not occur in these four
scenarios' hot loops, so "no change" is the expected, correct
result — the wins are concentrated where large allocations actually
happen: `large` and `pareto`.)

### Investigation: the server macro (ADR 0013) — no change

The baseline's one v2 loss (server, to v1) dissolved under scrutiny:
rankings inverted between batches, the benchmark's teardown was
inside the timed region (fixed), and at 2 threads v1 ≈ v2 (47–50
ns/op) with glibc at 65–82. Recorded as measurement noise; a real
verdict needs instruction counting, unavailable on this VM.

### Experiment 2: calloc memset skip (ADR 0012) — REJECTED before implementation

The motivating number was a throttling artefact; interleaved, v2's
calloc already beats glibc's. Not implemented.

## Final test status

- `test_basic` PASS under glibc, v1, v2, jit — extended with a
  large-block-cache section (dirty-block calloc zeroing, full-write
  after reuse, realloc growth) guarding ADR 0011's invariants.
- `bench/stress` PASS under all three builds (×3 runs each), and
  PASS under a `-DFM_DEBUG` build of v2 (invariant assertions on).
- `bench/check` PASS under all three builds.
- `bench/macro` all five scenarios complete under all four
  allocators; the benchmark itself is ASan-clean under glibc.
