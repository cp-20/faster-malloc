The five diagnostic trylock runs acquired all 87 attempted censuses;
there were **zero bail-outs**, versus zero of 82 blocking attempts. They
returned 1,572,864 bytes through whole-span unmapping and 983,040 bytes through
page purge in aggregate, versus 1,114,112 and 888,832 for blocking. New-span

reclamation through failed trylocks as the cause in this workload/session.
Counters are atomic, diagnostic-only, and excluded from throughput results.
A forced-busy self-check verifies that the bail counter really increments,
and that explicit trim subsequently acquires the mutex.

Cross has a single sustained freeing thread, so it normally has only one
census caller; neither explicit trim nor idle release is enabled. The original
harness's bounded ring calls sched_yield when full/empty. Diagnostic wait4
measurements record variable context switches (blocking voluntary 16–179,
trylock 50–101; involuntary 15–51 and 9–39), but do not isolate scheduler,
cache layout, ring pacing, or uncontended mutex API costs from each other.
The identical-binary experiment below produces a 3.21% median difference
without any allocator change. This establishes appreciable session/queue
variability, not proof that the entire +9.69% is noise. The persistent
cross-free regression remains disclosed; an exact residual cause needs a
quieter, CPU-controlled experiment. Do not attribute it to missed reclamation
or claim it fixed.

Diagnostic peak_kib is retained as raw wait4 evidence only: fork/exec can

## Use-case mining — offline data tools (round11/usecases)

This section belongs to the use-case task; crossfree findings belong in their
own section. Base: main `e598f28`. This is a measurement-only round: no allocator
implementation, default, or profile changes, and no claimed Pareto win.

### New cells and reproduction

Added `bench/apps/data_tools.py`, a standalone extension to the application
matrix alongside the round-5 cells. It uses two actual distro tools:

- **GNU sort**: single-threaded numeric-key sorting of a 400,000-row TSV event
  log, `sort --parallel=1 -S 128M -k1,1n events.tsv`. This covers ETL/log analysis
  with variable-length records and a large record-pointer buffer.
- **XZ**: single-threaded archival of that same log, `xz -T1 -6 -c events.tsv`.
  This covers real liblzma compression buffers/dictionaries, a different shape
  from the existing JSON, database, runtime, compiler, and server cells.

Input is generated offline using seed 11013; no runtime network access or
external source build is required. Both tools were already installed. The
script requires all four allocator libraries and at least five repetitions.
It clears inherited allocator tuning/profile variables and applies
`LD_PRELOAD` only to the tool child, not the Python measurement process.

```sh
make -j4
# This host had no mimalloc installed or apt package lists. Extract a distro
# binary locally (no sudo or system changes); only provisioning needs network.
mkdir -p work/packages
curl -fsSL https://deb.debian.org/debian/pool/main/m/mimalloc/libmimalloc2.0_2.0.9+ds-2_amd64.deb \
  -o work/packages/mimalloc.deb
dpkg-deb -x work/packages/mimalloc.deb work/packages/extracted
MIMALLOC_LIB="$PWD/work/packages/extracted/usr/lib/x86_64-linux-gnu/libmimalloc.so.2" \
  REPS=5 python3 bench/apps/data_tools.py
bash bench/round7.sh
```

Environment: Debian 13 x86-64, Linux 6.18.57, Intel Xeon Platinum 8573C,
3 visible CPUs, cgroup CPU quota 2 cores and memory limit 8 GiB. GNU coreutils
9.7, XZ Utils 5.8.1, glibc 2.41-12+deb13u4, jemalloc 5.3.0-3, mimalloc
2.0.9+ds-2. v2 uses the unchanged balanced default at the base commit.
Mimalloc package SHA-256:
`a20035605a532be3186f0f48607c7106fe2a5551066c29de663c965692c446c4`.

### Method and scope

All 40 samples ran in the same session, sequentially after the correctness
battery finished. Each tool gets one untimed glibc reference/warmup; the first
allocator rotates every repetition (glibc/v2/jemalloc/mimalloc). Each sample
runs a fresh process. Wall time and peak RSS reuse `run_timed.py`;
fixture generation, hashing and reference correctness checks are outside timing.
RSS is Linux `ru_maxrss` in KiB, not summed process-tree RSS. These tools have
one worker; the short-lived `env` launcher is also included in the process-tree
accounting. Medians for time and RSS are computed independently, not selected
from the fastest run. Filesystem cache is warm; no claim about cold-disk or
multithreaded performance is supported here.

The reference sort must pass `sort -c -k1,1n`; reference XZ decompression must
hash identically to the input. Every measured output must match the corresponding
reference SHA-256. A timeout, nonzero exit, missing library or differing output
fails the script rather than silently omitting a cell.

### Pareto gaps and tuning decision

**No measured Pareto dominance established.** Every v2 time range overlaps
all three competitor ranges on both tools. Sort is particularly short/noisy:
glibc's maximum is 0.622 s versus its 0.356 s minimum; the -14.03% median v2
time difference must not be treated as a demonstrated speed win.

- Sort: v2 has a smaller footprint than jemalloc (1,152 KiB, 1.91%, with
  disjoint RSS ranges), but loses footprint to glibc (512 KiB, 0.88%) and
  mimalloc (256 KiB, 0.44%), also with disjoint RSS ranges. Mimalloc wins both
  median axes over v2, though the speed ranges overlap. V2 versus glibc and
  jemalloc are median tradeoffs.
- XZ: glibc wins both median axes over v2: v2 is 1.49% slower and uses
  640 KiB (0.74%) more peak RSS. Only the footprint difference has disjoint
  ranges. V2 saves 2,048 KiB versus jemalloc (2.31%) and 10,496 KiB versus
  mimalloc (10.80%), with disjoint RSS ranges, but is slower by median
  (+1.39% and +0.21% respectively). Those are median tradeoffs, not dominance.
- All 40 measured outputs passed hash validation and all tool invocations
  exited successfully. This establishes correctness for these inputs, not a
  general robustness ranking between the allocators.

A bounded footprint investigation is justified by the **512 KiB sort** and
**640 KiB XZ** gaps against glibc: trace large-buffer allocation sizes and
resident metadata/rounding pages before considering a large-allocation layout
or release-policy change. This is a hypothesis, not an attribution: these
numbers alone cannot identify which allocator path causes the extra pages.
The potential total gains in these cells are under 1% RSS, and the workloads
have substantial live buffers. No candidate tuning was implemented or adopted;
there is no non-overlapping timing improvement to justify one. Any future
change must supply the measured disjoint-range win, ADR and green battery
required by the task. Longer sort samples would be appropriate before using
that cell to justify speed tuning.
