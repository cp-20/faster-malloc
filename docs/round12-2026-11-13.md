### Peak decomposition and mechanism selection

The existing round-10 header/pagemap/live-capacity probes were reused in
three separate instrumented Lua invocations, pausing every 10 ms and keeping
the largest synchronized RSS sample. These are not exact decompositions of
the uninstrumented wait4 HWM: instrumentation, sample timing and pauses
change the run. Median category values need not sum to median total.

| peak category | median (range), KiB |
|---|---:|
| total sampled RSS | 17,344 (17,284–17,352) |
| live API usable capacity, small + large | 9,030 (9,030–9,030) |
| live large mappings resident | 3,148 (3,148–3,148) |
| cached large mappings resident | 3,140 (3,140–3,140) |
| fully-free small spans resident | 2,304 (2,292–2,540) |
| partially-live small spans resident | 7,076 (6,884–7,128) |
| live small usable capacity | 5,894 (5,894–5,894) |
| other resident mappings | 1,632 (1,628–1,632) |

Live usable capacity is about 52% of this sampled peak; it includes allocator
rounding and oversized cache reuse and must not be equated to Lua's requested
live bytes. In particular, partial-span residency includes live data; it is
not all returnable. Cached large residency is the largest directly identified
fully-returnable component, ahead of fully-free small spans. This supports
attacking the growth trail rather than assuming the historical 40% proportion
or treating every partial-span byte as free.

One mechanism was prototyped: on cache admission, discard complete payload
pages of a bucket that has never served a cache hit in this thread. Preserve
its header page, mapping, links and cache budget. A first successful hit marks
the bucket warm permanently for that thread; later frees retain payload.
No profile is changed, no new timer or shared counter is introduced. The
prototype is controlled by `FM_LCACHE_COLD_PURGE=1` (default off when applied);
this is not a shipped runtime option. This can
pay extra zero-fill faults at first reuse, and a once-warm bucket never
automatically cools; it is a deliberately conservative reuse heuristic.

The paired Lua median improves by 3,052 KiB (17.1%); candidate maximum
15,220 is below control minimum 17,800 KiB. Lua time changes +1.0%, with
overlapping ranges; no time improvement is claimed. Lua still loses peak
RSS to glibc and mimalloc.

A second diagnostic build with the opt-in confirms that cached-large resident
bytes fall from 3,140 to 260 KiB in all three sampled runs. Its sampled total
is 14,432 (14,380–14,456) KiB, with the same 9,030 KiB live usable capacity;
small-span residency remains 9,384 (9,336–9,408) KiB. This supports the intended
attribution: discard the cache's cold payload rather than reduce live data.
The existing `churn2.lua` phase probe also reports roughly 7,640 KiB of Lua
requested live data near the peak (about 44% of baseline resident bytes,
versus about 52% measured as API usable capacity). Both definitions are
reported to avoid silently equating usable capacity with application live data.
Diagnostic observations are not throughput samples.

The confirmation shows that shared-container noise is substantial: even the
identical baseline repeat's many median is 10.0% above baseline. However,
the candidate many median remains 17.5% above baseline and 6.8% above the
identical baseline repeat; it is slower than each control in 7/10 follow-up

all fifteen primary pairs, the many slowdown remains material. Overlapping
ranges do not establish neutrality, so the guard gate is **not passed**.
Cross's initial concern does not reproduce in the ten-round median; local
and census ranges overlap. No universal speed/neutrality claim is made.

**Decision:** reject this implementation rather than ship it as a default or
opt-in. The measured Lua peak win is real in this session, and diagnostic
cache residency confirms the intended target, but the required guard gate
is conjunctive. Candidate-off numbers do not prove whether code layout,
reclamation, scheduling, or a combination explains the slowdown; do not
claim a causal diagnosis from these timings. No profile change or second
mechanism was attempted. ADR 0058 records the hypothesis, implementation,
ownership argument, measurements and rejection.

## Startup footprint — round12/startup-footprint

Base: `3d1e114`. This section owns the startup investigation; other round-12
sections are independent. [ADR 0060](adr/0060-smaller-first-span.md) records the
static adoption; [ADR 0061](adr/0061-smaller-first-span-jit-rejected.md) records

### Measurement controls

All runs share one cloud session, GCC 14.2, Python 3.12.14, Node v24.22.1, 4 KiB
pages and a two-CPU cgroup quota. The JSON fixture exactly matches round 10's
SHA256. Timing runs are serial and do not overlap builds or diagnostics.
Startup has seven rotated repetitions per app/variant/method. jemalloc is
installed; mimalloc is unavailable in this checkout/environment and was not
silently substituted. Baseline libraries were rebuilt at the requested base
and retained separately before changing the shared core.

The round-10 startup harness preloads **both** its Python timing wrapper and
the target. Reproducing it is necessary for comparison, but it overstates a
Python-only startup measurement: baseline v2 reports 13,312 KiB with the
preloaded wrapper versus 10,112 KiB when only the target is preloaded. Both
methods are retained. The target-only path still launches through an ordinary
Python driver/env; its low RSS results are subject to the driver/fork reporting
floor. Synchronized `/proc` HWM/RSS snapshots provide an independent check, with
the explicit limitation that their snippets add an `os.kill`/`process.kill`
stop operation before exit. They are not the exact no-op workloads.

### Attribution

Three paused startup snapshots per configuration use the **real** libraries,
read span headers and resident bits, and sum synchronized smaps categories.
The following are median KiB (static v2):

| Component | Python base | Python candidate | Node base | Node candidate |
|---|---:|---:|---:|---:|
| Small-span mappings (virtual) | 4,736 | 1,816 | 6,528 | 3,828 |
| Small-span resident pages | 4,292 | 1,668 | 6,104 | 3,600 |
| Large-block resident pages | 148 | 148 | 1,300 | 1,300 |
| Allocator file-backed resident pages | 52 | 52 | 52 | 52 |
| Other anonymous resident pages | 1,028 | 1,016 | 5,656 | 5,640 |
| Other named resident pages | 4,700 | 4,700 | 15,792 | 15,800 |
| Anonymous executable pages (runtime/JIT combined) | 0 | 0 | 2,084 | 2,084 |
| Total RSS at stop | 10,220 | 7,584 | 30,988 | 28,476 |

These are snapshot medians, not an additive decomposition of a different
instant's historical maximum. In particular, the other categories are not all
allocator waste. glibc's corresponding total RSS is 6,408 KiB (Python) and
25,648 KiB (Node); its named/anonymous split differs because libc heap pages
and runtime direct mappings are not v2 spans.

A separate diagnostic build reuses round 10's live usable-byte accounting.
Live small capacity is unchanged: 466.89 KiB Python, 1,056.34 KiB Node. Base
small usable capacity is 4,576.62/6,297.11 KiB, versus 1,703.02/3,615.34 KiB with
the candidate. Live capacity cannot be subtracted from RSS to claim exact
fragmentation. Python small spans grow in count from 74 to 81 and Node from
102 to 116, while their mapped/resident bytes fall substantially: classes that
need more space subsequently get ordinary full spans.

The diagnostic separates other candidate explanations (medians):

- Batch-page metadata: Python 20 -> 8 KiB; Node 44 -> 28 KiB. It is included in
  the anonymous residual above, not added again.
- No startup census calls, hence no census scratch mapping at the stop.
- Central array: 8.0625 KiB nominal (129 cache-line entries), covering 12 KiB
  of resident pages including shared boundary pages; unchanged.
- ELF TLS: static 3.4922 KiB per thread, JIT 3.5078 KiB. Python has one thread,
  Node seven (nominal static total 24.4453 KiB). These are layout sizes, not
  separately attributable RSS. The first-span marks add only 129 B process-wide.
- JIT histogram: 32 KiB nominal; resident pages covering it total 24 KiB Python
  and 16 KiB Node, including shared boundary pages. With matching span policies, JIT startup RSS exceeds
  static by only about 16–28 KiB (before and during the shared-policy experiment). Anonymous executable residency equals the
  static/glibc runtime control, with no measured additional startup code mapping.
- Cached large pages: Python 12 KiB, Node 408 KiB; live large pages about
  136/892 KiB. These do not change with the candidate. They explain why the
  shortlived large-cache preset cannot remove the dominant small-span cost.

The dominant residual is link-word initialization across the first 64 KiB span
of every used class, rather than an eager reservation of all 129 classes or a
large TLS/JIT arena. Alignment mmap temporarily reserves an extra 64 KiB plus
one page and immediately unmaps its excess; untouched alignment slack does not
explain resident high-water marks. Keeping the first mapping at 16 KiB (or enough for one
large-class block) saves 2,624 KiB of small-span residency in Python and
2,504 KiB in Node while preserving the existing 64 KiB growth policy.
