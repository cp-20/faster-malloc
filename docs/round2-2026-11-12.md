# Round 2 — locality, memory return, and an honest rejection, 2026-11-12

Branch: `round2/locality-and-trim`. Decisions are recorded as ADRs
(0014, 0015, and an update to 0010); this log holds the narrative
and the numbers.

## The short version, in plain language

Round 1 left two known weaknesses (README §6, ADR 0010):

1. When memory is freed and reused, v2's reuse is *scattered* — a
   burst of new allocations lands all over the heap instead of
   concentrating on a few memory pages, the way mimalloc manages.
   Scattered reuse is slower on real hardware because the CPU's
   caches work at page granularity.
2. v2 never gave memory back to the operating system. Once it had
   taken memory, it kept it.

This round attacked both, and the two attacks had opposite
outcomes:

- **Memory return: solved.** `malloc_trim` — the standard "give
  back what you're not using" call — used to be a stub for small
  allocations. It is now real: it inspects the allocator's shared
  free lists, proves which 64 KiB spans are completely empty, and
  unmaps exactly those. In the new `trim` benchmark, a program
  that used 157 MB and freed it all now drops to **7.0 MB** of
  resident memory after asking for a trim (glibc: 2.8 MB; v2
  before this round: 135 MB — it barely trimmed at all). The
  mechanism costs nothing measurable on the fast path.
- **Free-list shaping: built, measured, and rejected.** We
  implemented the textbook fix for scattered reuse (group freed
  blocks by the span they belong to, so reuse drains one span at a
  time). It worked exactly as designed on the metric we built for
  it — a reallocation burst's footprint fell from **513 pages to
  68** (the floor is 64) — and it still made every real workload
  *slower*. The reason is interesting and is written up in ADR
  0014: in realistic programs, blocks allocated together are
  mostly freed together, so free order already groups them by
  span, and there is little scatter left to remove; the fix's cost
  (touching every recycled block one extra time) is paid whether
  or not there was scatter to fix. The code was removed; the
  measurements stay, so nobody has to re-run this experiment to
  know.

There is also a new interactive demo (`demo/index.html`) that
simulates the allocator's design in the browser — spans, free
lists, the central batch stack, both recycling modes above, and a
working trim button — next to tables of the real measurements.

## What was measured, and how

Same environment caveats as round 1: a shared, CPU-capped VM
(~1.5 CPUs), wall-clock min-of-N with allocators interleaved, and
glibc/v1/jit as controls. Two additions this round:

- `locality` (bench/macro): a deliberately hostile pattern —
  free a 32,768-block working set in scrambled order, reallocate
  an eighth of it, and *count the distinct 4 KiB pages* the burst
  lands on. Address counts are bit-stable across runs, which
  makes this the one noise-free metric available on this VM.
- `trim` (bench/macro): build ~157 MB, free it, `malloc_trim(0)`,
  and read resident memory at each stage.

Macro baseline for the round (ns/op, this round's first session;
v2 RSS in KiB) and the final state are below; the host drifted
between sessions, so comparisons use ratios to glibc within a
session, with the unchanged v1 as a drift control.

## Experiment 1: free-list shaping (ADR 0014) — REJECTED

Design: at flush time, walk the detached local list, group blocks
by span into a per-thread *span stash*, publish overflow groups
span-pure, and let refills drain the largest group first.

Getting there took two debugging rounds, both recorded in the
ADR:

- The first version also unmapped a span the moment a group
  completed it. On batch/hold-style rounds (allocate a lot, free
  it all, repeat) that is an munmap + mmap + page-fault refill
  *per span per round*, and it cost 3–6× (batch 10.7 → 66.5 ns/op).
  Releasing memory is `malloc_trim`'s job, not the free path's —
  the same conclusion glibc's design encodes.
- The first walk was also unbounded: a flush detaches the whole
  local list, which is mostly the *untouched remainder* of the
  last refill, not fresh frees. Single-block churn walked 3,837
  blocks every 256 operations. Bounding the walk to the freed
  prefix (`kClassLimit + 32`) and adding a single-span fast path
  fixed that.

Final shaped build, locality: **67.8 pages/burst** (baseline
512.9, floor 64). And yet, v2/glibc ratios before → shaped:

| workload | before | shaped |
|---|---|---|
| compiler | 0.49 | 0.58 |
| jsondoc | 0.76 | 0.84 |
| kvstore | 0.83 | 0.89 |
| game | 0.28 | 0.31 |

Micro agreed (batch 8.6 → 15.5, hold 11.0 → 20–32, rand 86.9 →
217.0 ns/op), and server peak RSS rose with stash retention
(11,296 → 16,928 KB). Verdict: the grouping tax — at least one
extra pointer chase per recycled block — exceeds the locality it
buys, because in these workloads free order already clusters by
span. Rejected and removed; ADR 0014 keeps the numbers and names
the untried variant (regroup at refill, on the allocating thread)
for future work on hardware with cache counters.

## Experiment 2: malloc_trim census (ADR 0015) — KEPT

Batches now record their length and span-purity where the
publisher knows them for free (the fresh-span rest at refill).
`malloc_trim` flushes the caller's local lists, detaches each
class's central stack atomically, counts free blocks per span,
and unmaps spans whose count equals their block count — a proof,
not a heuristic: every block exists exactly once across all the
allocator's lists, so a span with all its blocks in the central
list has no live blocks and none parked anywhere else. Other
threads' local lists are out of reach, which only under-counts
(the safe direction).

| allocator | live | after free | after trim |
|---|---|---|---|
| glibc | 150.9 MB | 124.8 MB | 2.8 MB |
| v2 before round 2 | 157.3 MB | 161.6 MB | 135.2 MB |
| **v2 after round 2** | 157.4 MB | 161.7 MB | **7.0 MB** |
| jit after round 2 | 157.4 MB | 161.7 MB | 7.1 MB |

The residual ~4 MB over glibc is process baseline, spans pinned
by a few live libc/stdio blocks, and batch-pool pages; a
controlled single-class diagnostic lands at near-parity with
glibc (3,468 → 2,216 KB vs 3,508 → 1,944 KB). Hot-path cost:
none measurable — same-minutes probes against the pre-round-2
build are identical within noise (churn 8 B 6.76 vs 8.74, batch
8.78 vs 8.79, hold 11.24 vs 11.16 ns/op).

## Final verification

Macro suite, final build (ns/op; compare the ratio column, the
host drifted): v2/glibc — compiler 0.47, jsondoc 0.75, kvstore
0.87, game 0.26, locality pages 512.9 (the documented, now
precisely measured standing gap), trim after-trim RSS 7,008 KB.
Micro suite: v2 at parity with the pre-round-2 baseline on every
scenario (churn 6.7–6.8, batch 8.4, rand 72.0, hold 10.8, threads
5.6, large 9.6, touch 6.1 ns/op). `server` remains the noisy
outlier it was in ADR 0013.

Correctness: `test_basic` (extended with a span-release section:
span-filling allocations freed and trimmed in rounds, and a live
set held across a trim and verified afterwards), `bench/stress`
×3, `bench/check`, `bench/mt`, and the whole macro suite pass
under v1, v2 and jit; v2 also passes stress and test_basic under
an FM_DEBUG build (invariant checks + a census over-count
assertion).

## The demo

`demo/index.html` — a self-contained page (no dependencies, works
from `file://`) with a JavaScript simulation of the v2 design:
size classes, 64 KiB spans, per-thread free lists and limits, the
central batch stack, the large-block cache, and a census trim
button. Workload patterns mirror the macro scenarios, and a
recycling-mode toggle switches between free-order recycling (v2
today) and the span-grouped recycling of ADR 0014, with the
burst page-footprint shown live — the rejected experiment,
playable. The real measured tables (instruction counts, macro
results, the locality and trim numbers) are charted below the
simulation, labelled as measurements, distinct from the
simulation's illustrative timings.

## What's next

- Refill-side regrouping is the untried shaping variant (ADR
  0014); it wants a machine with cache counters to price fairly.
- The JIT branchless-dispatch idea (README §6.3) was not touched
  this round: with shaping rejected, the JIT's static path is
  unchanged, and the round's budget went to the two items above.
- Batch-pool pages are never returned; a bounded pool free-list
  drain could join the trim census cheaply.
- Thread exit still strands per-thread state (local lists, the
  large cache); a destructor-based flush is the known fix and is
  now more valuable, since trim gives the flushed blocks somewhere
  provable to go.
