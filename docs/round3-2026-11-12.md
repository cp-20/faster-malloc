# Round 3 — real applications, robustness, and bounded retention

*2026-11-12. Branch `round3/real-apps`. ADRs 0016–0019.*

## In plain language

Until now, this allocator was mostly tested against benchmarks
written for it. This round pointed it at real programs instead —
a database server, a JSON tool, four language runtimes, a compiler
— and compared it against the allocators those programs normally
use, including the three big production ones (jemalloc, mimalloc,
tcmalloc). Three things came out of that:

1. **A real crash, found and fixed.** Under Node.js, the JIT build
   crashed before the program even started, because Node's own
   startup code allocates memory before our library's initialiser
   runs. That class of bug — "works in our tests, dies inside a
   real program" — is exactly what this round was for. Fixed, with
   a regression test that loads the allocator the same way Node
   does (ADR 0016).
2. **Threads no longer leak the allocator's memory.** Worker
   threads that were created, did work, and exited used to strand
   everything they were holding — in the new stress test, 83 MB
   stayed behind after just 72 short-lived threads. Now a thread
   hands everything back when it exits: 83 MB became 3 MB
   (ADR 0017).
3. **The memory ceiling is bounded now.** The allocator's
   large-block cache could hold on to gigabytes of freed memory
   per thread. It is now capped at 64 MB per thread, chosen from a
   measured sweep: real programs' peak memory dropped noticeably,
   and nothing we measured got slower (ADR 0019).

One idea that looked obvious — growing big blocks in place with
the OS instead of copying them — turned out to be a trap and was
rejected with measurements (ADR 0018). Details below.

## The app matrix

Eight real workloads × seven allocators, `LD_PRELOAD` swapped per
run, min-of-3 interleaved rounds on this (noisy, shared) VM,
wall-clock seconds and peak RSS in MB. Every cell also had to pass
a correctness check ( checksums, round-trips, full test suites'
exit codes); a crash or wrong answer would be recorded as a FAIL,
not a slow time. **There were no failures in 56 combinations, in
either the baseline or the final run.**

How to read this honestly:

- **Speed: v2 is in the leading group almost everywhere** —
  fastest or within noise of fastest on redis, jq, lua and gcc;
  level with everyone on sqlite and git; a few percent behind the
  best on python and node, where the runtime's own memory manager
  (CPython's pymalloc, V8's GC heap) does most of the work and the
  libc allocator only sees the overflow. That ceiling is real and
  no allocator in the table escapes it.
- **Footprint: better than round 2, still not glibc.** Versus the
  round-3 baseline run of the same matrix, the final build cut
  Python's peak from 565 MB to 506 MB and Node's from 544 MB to
  512 MB (the 64 MiB cache budget). The remaining excess over
  glibc is the small-object design: 64 KiB spans and per-thread
  free lists that are only returned on `malloc_trim` (ADR 0015)
  or thread exit (ADR 0017). Lua shows this most clearly —
  fastest time in the table, +66% RSS — because its workload is
  almost all small blocks.
- **Session noise is real.** The baseline run had redis at 3.09 s
  for v2 vs 2.35 s for glibc; the final run has 2.31 s vs 2.64 s.
  Same code path, different afternoon on a shared VM. Single
  cells should be read as bands, not rankings; the patterns that
  repeat across both runs (jq/lua/gcc strength, python/node RSS
  excess) are the ones to believe.

The harness is `bench/apps/` (`apps.sh`, `prep.sh`, workloads for
Lua/Python/Node churn, a 200k-record JSON fixture, a synthetic
1,500-commit git repo, SQLite speedtest1, redis-benchmark with a
round-trip check). It is part of the repo now and rerunnable.

## Bugs found and fixed

- **JIT build crashed Node.js at startup** (found before this
  round's writing, fixed on this branch, `7d24e8d`, ADR 0016):
  entry points jumped through a function pointer that only the
  library constructor fills in; any earlier allocator call — Node
  has C++ static initialisers in a dependency library that run
  first — segfaulted. Entries now start on the generic path.
  Regression test `bench/earlyinit.sh` emulates the load order.
- **Thread-exit retention** (ADR 0017): described above;
  82.9 MB → 2.9 MB final RSS in `bench/tlsexit`.
- **FM_DEBUG canary missing in the JIT `free`** (found while
  building the thread-exit drain): debug builds of the JIT
  asserted on ordinary frees. Fixed in the same commit.
- **API audit — no gaps found.** calloc/reallocarray overflow,
  `posix_memalign` invalid alignments, `malloc_usable_size` on
  aligned blocks and NULL, fork behaviour: all correct under v2
  and JIT. The checks are now a permanent section of `test_basic`.

## Optimisation attempts

- **realloc fits-check — kept** (ADR 0018, variant A). Growing a
  large block into room its mapping already has (frequent after a
  cache reuse) no longer copies. Pointer stability is
  regression-tested.
- **mremap growth — rejected** (ADR 0018). In-place extension
  almost never fires in a live heap; the moving variant's natural
  sketch is unsafe (the span header can land *before* the moved
  mapping — caught by a forced-move experiment, not by luck), and
  the safe variant measured 7.9× *slower* on the growth ladder
  because it bypasses the large cache, which was already doing
  the same job with resident pages (faults: ~10k → ~1.02M).
  Lua's single-growing-string pattern gained 6.5%; not worth it.
- **Large-cache budget 4 GiB → 64 MiB — kept** (ADR 0019), from
  the five-point sweep in that ADR. 32 MiB bought a little more
  RSS but cost 9× on the growth ladder; 256 MiB kept the
  synthetic pareto scenario at full speed and bought almost no
  RSS. 64 MiB is the knee.

Macro suite (`bench/macro.sh`) on the final build: no regressions
— compiler 36.3 ns/op, jsondoc 103, game 22.1, locality 6.8 (all
best-in-table), kvstore at parity, server still the known weak
scenario (ADR 0013), trim still lands a freed 157 MB working set
at ~7 MB RSS.

## What remains

- **Small-span retention** is now the whole footprint story:
  spans are never returned except by `malloc_trim`. An automatic,
  pressure-driven return that doesn't repeat ADR 0014's measured
  failure is the open design problem.
- **The server macro scenario** still trails glibc; ADR 0013
  closed the last investigation as noise, but the gap reappears
  often enough to deserve a dedicated look with a quieter machine.
- **Refill-side regrouping** and **JIT branchless dispatch**
  (README §6) remain untried.
- The interactive demo (`demo/index.html`) still presents
  round 1–2 measurements; they are labelled as such and remain
  accurate history, but the round-3 app matrix is not in it yet.
