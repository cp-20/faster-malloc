# Round 4 — 2026-11-12: memory comes back on its own

## What this round did, in plain language

Round 3 ended with a clear embarrassment: the allocator was fast,
but it *kept* memory. Programs that peaked and then shrank stayed
fat — Lua ended its run holding 19.8 MB where glibc held 9.0 MB,
and almost all of the difference was small-block spans that were
completely free but still mapped, returnable only if the program
thought to call `malloc_trim`.

**That is now fixed — carefully.** v2 watches its own free lists:
when a whole 64 KiB span has been completely free for a while
(100 ms), it is handed back to the operating system automatically,
no `malloc_trim` required. In a purpose-built test (free a
~130 MB working set, then keep the process lightly busy), v2's
resident memory falls from 135 MB to **9.5 MB within about
300 ms**, while glibc — which only returns memory when asked —
sits at 124.9 MB forever.

The "for a while" is the whole design. The first version of this
feature returned spans *immediately*, and it was a disaster in
exactly the place ADR 0014 predicted: workloads that free a
working set and immediately reallocate it (our batch/hold/
locality benchmarks cycle every ~3 ms) paid 8–40× slowdowns
re-mapping what they had just given back. The shipped version
marks a dead span, waits 100 ms (about 25 cycles of those
workloads), and only then unmaps — and on every cyclic workload
measured, the speed cost is zero within noise, while the
batch/hold/locality numbers are bit-for-bit their old selves.

One scare along the way, caught *because* the full matrix was
re-run before merging: the first version of the release
machinery made **jq 40 % slower**. jq's DOM phases leave free
lists hundreds of thousands of blocks deep that are mostly not
dead, and the census kept walking them every ~10 ms. The shipped
version prices each census and spaces a class's visits in
proportion to what the last walk cost (a huge stack is revisited
every few seconds; a small dead one, immediately) — jq is back
at parity with the pre-feature build, and the probe still lands.
ADR 0020's revision section has the bisection.

Three other investigations round out the round, all with honest
negative or null results:

- **The sqlite and node "gaps" from round 3 were chased with a
  request-stream profiler and not found.** sqlite's gap flips
  sign between measurement sessions on this noisy VM (it was
  +5.6 % for glibc in round 3 and −8 % in one round-4 session,
  with the unchanged v1 as a steady control), and node's entire
  malloc stream (~168k calls) is arithmetically too small to
  produce its supposed 0.1–0.2 s deficit. No code change was
  justified; ADR 0023 records the profiles so a future round on
  quieter hardware starts from evidence.
- **Refill-side regrouping works and was still rejected.**
  Grouping recycled blocks by span when a refill pops them (the
  variant ADR 0014 left open) reproduced the locality win —
  512.9 → 67.7 pages per burst, near the floor — but the walk it
  costs (~22 ns per cold block) taxed batch/hold by ~35 %, the
  same trade that sank the flush-side version. ADR 0021.
- **The JIT jump table never beat the range tests.** Implemented
  exactly as long planned (a 2049-entry table indexed by size
  bucket, provably identical dispatch), it lost ~13 % where one
  hot class dominates, tied at four classes, and lost 3–9 % on
  the real macro workloads: the range tests are register-only and
  well predicted, the table pays a dependent load and an indirect
  branch on every call. ADR 0022.

for this round's data: the full app matrix (switchable by app,
metric and round) and the span-return decay curve (drag the time
slider), plus the round-4 locality result.

How round 4 changed the reading of round 3's table:

- **sqlite's time "gap" is gone in this session** (v2 at parity,
  1.02×, after measuring 0.92× in this round's subset session),
  consistent with ADR 0023's verdict that the sign of that cell
  is a property of the afternoon, not the allocator.
- **RSS is mostly unmoved, and we now know why, app by app:**
  python's and node's peaks are *live* peaks (the parsed JSON,
  the V8 heap) — there is nothing dead to return at the moment
  the peak is set. Lua's excess is a partially-free steady state
  (~+2 MB) plus a terminal burst freed in the last milliseconds
  before exit, inside any decay window. redis's retained spans
  are partially free. The automatic return fixes the pattern it
  can fix — a process that shrinks *and keeps running* — which
  the matrix's short-lived apps mostly are not.
- One small honest cost: the server macro scenario's RSS sits
  ~1.1 MB above its pre-round-4 reading (11.6 vs 10.4 MB) — the
  per-class retention quota plus spans marked but not yet aged.
  Bounded, and the price of the hysteresis.

## Correctness

Full battery green on the shipping build for v1/v2/jit:
test_basic, stress ×3, check, mt (both modes), earlyinit,
tlsexit (v2 final RSS 2,836 KB), and FM_DEBUG builds of both v2
and the JIT (including the census over-count assertion under the
automatic release). One pre-existing harness defect was found and
documented, not fixed: `bench/micro`'s `cross` scenario races its
own ring buffer (the producer laps the consumer and a slot is
freed twice) — it aborts with a tcache double-free under *stock
glibc*, unchanged since the harness's first commit.

## Environment incident (for the record)

Mid-round, the VM restarted and rolled back to an image without
round 3's distro packages (redis, lua5.4, jemalloc/mimalloc/
tcmalloc) and with an empty /tmp (all scratch probes were
rebuilt or their results already recorded; no repository state
was lost — git history is the round's spine). The final matrix
above was measured after the host's package-intent replay
restored the documented provisioning.

## ADRs this round

- **0020** — automatic span release with dead-span ageing
  (accepted; includes the rejected instant-release form and its
  numbers).
- **0021** — refill-side regrouping (rejected: locality
  512.9 → 67.7 pages, batch/hold tax ~+35 %).
- **0022** — JIT jump-table dispatch (rejected: never beats range
  tests in the JIT's operating envelope).
- **0023** — sqlite/node gap investigation (no defect found;
  profiles recorded).

## Round 5 backlog, in order

1. **Partially-free spans are the remaining RSS problem.**
   Lua's steady-state +2 MB, redis's +37 %, and the general
   "RSS above glibc in most apps" all trace to spans that are
   *mostly* dead but not provably dead. The lever is placement,
   not return: prefer handing out blocks from the *fullest* span
   (so spans empty completely and become returnable), i.e.
   occupancy-aware refill — pick the central batch whose span is
   closest to fully free, or keep a per-class "current span"
   bias. Design and measure carefully; it touches the refill
   path everything depends on.
2. **Re-run sqlite/node on quieter hardware if it ever becomes
   available** (ADR 0023's profiles are the baseline), and price
   glibc's in-place top-of-arena realloc extension there — the
   one structural advantage found this round with no span-design
   analogue yet.
3. **Fix the `cross` micro scenario's ring race** (producer must
   not lap the consumer), so cross-thread free throughput is
   measurable again.
4. **Tune the release constants against a wider sweep**
   (FM_RELEASE_AGE_MS 100, the 1 ms-per-100-walked-blocks
   interval rule): they are single-point choices on a noisy VM;
   a small grid over the decay probe + cyclic micros + a
   jq-shaped deep-stack workload would show how sharp the
   optimum is — worth doing before anyone ports the policy.
5. **Idle-process release**: a process that goes quiet after a
   burst keeps its spans until its next allocation (ticks ride
   the flush path). A timer-based fallback (one timerfd thread?
   signal-based?) has fork/exec/signal-safety costs that need a
   design pass before any code; glibc has the same limitation,
   so this is polish, not parity.
