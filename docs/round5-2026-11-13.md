# Round 5 — use cases first: occupancy placement, profiles, four new cells, and an honest Pareto score

*2026-11-13. Continues from `docs/round4-2026-11-12.md`. This round
was worked by two successive workers (the first was interrupted
overnight; its committed work was verified, not redone) and its
direction was set mid-round by the project's owner: stop chasing
raw speed against allocators that have had decades to evolve.
Instead, mine real-world use cases, handle all of them well, treat
memory efficiency as a first-class axis next to speed, allow
per-use-case tuning profiles — and score the result honestly,
Pareto-style: per use case, is v2 better, tied, or still behind,
and why?*

## The short version

- **Placement learned about occupancy.** The census that already
  walked the spans to reap dead ones (round 4) now also regroups
  the survivors: blocks of a span are re-linked into one chain and
  the central stack is re-published fullest-span-first, so refills
  drain the fullest spans and the freest spans rest at the bottom,
  can empty, and can be reaped (ADR 0024). The consolidation probe
  that exists to measure exactly this settled at **9.0 MB RSS,
  down from 17.8 MB** — and past glibc's 19.2 MB on the same probe.
- **The knobs became a product surface.** Everything the census
  does is tunable at runtime: `FM_PROFILE=balanced|throughput|
  footprint` plus per-knob `FM_*` overrides, parsed once, never on
  a hot path (ADR 0027). The defaults are round 4's constants,
  which a full sweep showed sit on a flat optimum (ADR 0026).
- **Four new use cases joined the matrix:** nginx under HTTP load
  (with p50/p99 latency), PostgreSQL/pgbench, Ruby, and *bursty* —
  a server-shaped heap that ramps, idles, ramps higher, drains and
  idles again, built to ask the daemon question: does freed memory
  actually leave while the process lives on?
- **The honest score** (§4): v2 now dominates where memory is
  fragmented or freed-and-idled, ties glibc on time almost
  everywhere, and still loses peak RSS on short-lived apps whose
  peak is simply *live* when measured — plus one clean loss to
  mimalloc, which purges memory at page granularity while v2
  releases at span granularity. That gap is round 6's first item.

## 2. Occupancy-aware placement, and what it bought (ADR 0024)

Round 4 ended with a diagnosis: the remaining RSS gap was
*partially-free* spans — a span with three live blocks is pinned
just as surely as a full one, and free-order recycling scatters
survivors across ever more spans. Round 2 had tried to fix the
scatter twice (at flush, at refill) and been rejected twice: the
walk cost more than the locality bought (ADRs 0014, 0021).

The round-5 insight is that round 4 changed the economics: a
census already walks every span on a cadence to find dead ones.
Regrouping is a by-product of a walk that is already paid for.
Each census now links a span's surviving blocks into a single
chain and re-publishes the central stack as span-pure batches,
largest free-count first pushed with the freest chains spliced
just behind the stack top: refills draw from the fullest span, so
freest spans receive no new blocks, finish emptying, and get
reaped by the same machinery as dead spans.

Measured effect (same session, A/B against the round-4 build):

| instrument | round-4 build | round-5 build | glibc |
|---|---|---|---|
| consprobe settled RSS | 17.8 MB | **9.0 MB** | 19.2 MB |
| macro/micro ratios | — | unchanged | — |
| redis / jq (time, RSS) | — | flat | — |
| lua peak RSS | — | +0.2–0.5 MB | — |

The lua regression is real, characterised in ADR 0024 (regrouped
chains drop a class back into cache-block units; lua's terminal
burst is exactly the pattern that notices), and is the reason the
footprint profile exists as a tested answer rather than a hope
(§5). No hot path changed: regrouping happens only inside the
census, and the debug build asserts chain length == free count on
every regrouped span.

Two companion studies closed questions instead of opening code:

- **Release-constant sweep (ADR 0026).** Age, keep-count, census
  interval divisor and regroup threshold were swept on the probes
  and apps. The shipped defaults sit on a flat optimum: age moves
  release latency ~1:1 and nothing else; the census interval
  divisor (100) is the knee — 400 buys ~4% RSS for ~7% deep-stack
  time, 25 reverses the trade; `FM_REGROUP_MIN=8` is the measured
  sweet spot. The profiles in §5 are set from this sweep, not from
  intuition.
- **Size-class audit (ADR 0028).** Measured with `usableprobe`
  (usable ÷ requested, 1.0 = perfect): for 1–512 B requests v2's
  arithmetic table is the best of the field at **1.127**
  (jemalloc/mimalloc 1.130, tcmalloc 1.096, glibc 1.176); for
  513–8192 B glibc's exact bins win (1.003) with v2 second
  (1.022) and the geometric tables far behind (1.076–1.089).
  Verdict: no table revision — v2's remaining waste lives in
  partially-free spans (§1's problem), not in its classes.

## 3. Four new use cases (and two harness bugs that were not the allocator's)

Each new cell follows the matrix conventions: all seven
allocators, min-of-N, peak RSS, and a correctness gate that turns
a wrong answer into a FAIL, never a footnote.

**nginx** — 2 workers serving static files under a bundled
`wrk.c` load generator (20 keep-alive connections, 10 s), rps +
p50/p99 + summed peak RSS, body diffed. Its first runs failed
*every* allocator including glibc, twice, for two different
harness reasons: nginx closes a keep-alive connection after
1000 requests by default and wrk drives ~3500 per connection, so
every run reported exactly 20 "errors" (one per connection) with
identical bytes; and a stale master from an aborted run once held
the port, serving a deleted docroot to all seven allocators. The
config now raises `keepalive_requests`, the script kills stale
`fm-nginx` masters before starting, and the RSS sampler counts
only the master's own process tree.

**pgbench** — PostgreSQL 16, scale 5, 4 clients, 15 s, server as
`nobody` with the preload crossing via the environment; 0 failed
transactions required.

**ruby** — a string/array/hash churn workload with a checksum;
a third managed runtime next to CPython (which pre-empts the
allocator for small objects) and V8 (which owns its heap).

**bursty** — the round's thesis as a program: ramp to ~60 MB,
idle, ramp to ~90 MB, cohort-drain to ~10 MB live, idle again.
Phases are op-counted, so every allocator does identical work and
must produce the identical checksum. The columns that matter are
the idle-phase RSS values: what a long-running daemon actually
costs while it waits.

| v1 | 12,819 | 101 µs | 428 µs | 16.9 MB |

**bursty** (MB; the daemon cell):

| allocator | peak | idle 1 | idle 2 | time |
|---|---|---|---|---|
| glibc | **103.5** | **73.1** | 103.7 | 7.64 s |
| v1 | 106.1 | 75.8 | 106.3 | 7.55 s |
| v2 | 109.5 | 75.9 | 88.2 | 7.66 s |

Read the idle-2 column as three behaviours: jemalloc, tcmalloc,
v1 and glibc hand back essentially nothing after the drain (the
memory stays resident for the process's life); v2 gives back
~21 MB on its own, with no `malloc_trim` call, purely from ageing
+ occupancy placement; mimalloc gives back ~56 MB and wins the
cell outright. The mechanism matters: mimalloc can purge
individual free *pages* inside a segment, while v2 releases whole
64 KiB spans only, and bursty's survivors — a few live blocks per
span after a cohort drain — pin the rest. Round 6's first item
(§7) is page-granular soft return, with ADR 0014's lesson kept in
view: eager unmapping has been measured and rejected before, so
it goes through the census, aged, like everything else that
worked.

(v1 omitted here for width; it sits between glibc and v2 on RSS
throughout and is in the raw run. Bold = best in row, per column
type.)

**Per-use-case verdicts for v2 (balanced):**

- **Dominates:** the fragmentation instruments — consprobe
  (9.0 MB settled vs glibc 19.2, best of the field) and
  decayprobe (returns a freed 130 MB working set to ~10 MB in
  ~300 ms; glibc returns nothing without an explicit trim).
  Bursty idle-2 against five of six rivals (§3).
- **Wins:** lua on time (0.76× glibc), git on time (0.93×),
  pgbench on lowest RSS.
- **Ties:** time vs glibc on redis, sqlite, jq, gcc, nginx
  (all within ±3%); ruby outright; pgbench on throughput
  (session-dependent, §3); nginx p50/p99 mid-pack.
- **Still loses, with reasons:**
  - *Peak RSS on short-lived apps* (sqlite +48%, lua +63%,
    git +22% vs glibc): the peak is reached before ageing can
    act, and part of it is simply live. This is the retention
    price of the local caches; the footprint profile is the
    lever (§5).
  - *python/node peak RSS* (+15–17% vs glibc): live peaks —
    pymalloc arenas and V8's heap are allocated and held. Round
    4 established there is nothing dead to return; round 5's
    footprint profile cuts most of the gap anyway by capping the
    large-block cache (§5).
  - *bursty idle-2 vs mimalloc* (88.2 vs 53.6 MB): span-granular
    vs page-granular release (§3). The round's clearest loss.
  - *nginx throughput/tail vs jemalloc* (+6% rps, p99 299 vs
    442 µs): jemalloc's home ground (multi-process small-object
    churn); v2 ties glibc instead. Recorded, not chased.

That is the honest shape of "complete upper compatibility" after
five rounds: v2 is never the wrong choice on time, is the best
choice when memory is fragmented or freed-then-idled, and is
still not the smallest resident footprint for brief, dense,
exit-fast processes — where the memory it holds longer is the
price of the caches that make it fast.

## 5. Profiles: what they are and when to use which (ADR 0027)

`FM_PROFILE` picks a bundle; any `FM_*` knob overrides one value
(full table in ADR 0027). Parsing is lazy and one-time
(`pthread_once` on the first slow path), so pre-constructor
callers are unaffected (ADR 0016's constraint), and the profiles
were verified to cost exactly nothing on the hot path: batch /
hold / churn micro at 12.2 / 17.2 / 10.3 ns/op under all three
profiles, spread ≤1.5% (noise).

Validation across the instruments and the matrix (RSS in MB;
app rows are v2 under each profile, this session):

| measure | balanced | throughput | footprint |
|---|---|---|---|
| consprobe settled | 9.0 | 17.8 | 8.9 |
| decayprobe: lands / final | 250 ms / 9.9 | never in window / 135.5 | 100–150 ms / 8.1 |
| bursty idle 2 | 87.5 | 92.8 | 84.6 |
| python peak | 494 | 500 | **442** (−10.6% vs balanced) |
| node peak | 493 | 529 | **447** (−9.4%) |
| jq peak | 383 | 392 | **367** (−4.1%) |
| redis peak / lua peak | 10.1 / 18.8 | 10.1 / 19.2 | 10.2 / 19.1 |

(App-pass wall times are not compared across profiles: host load
shifted between the sequential passes, visibly and by a lot. The
RSS columns and the probes are the load-insensitive evidence,
plus ADR 0026's sweep for the time side of the census knobs.)

Reading: **throughput** is deliberately lazy — on probe
timescales it barely releases or consolidates at all (its
consprobe number *is* the pre-round-5 baseline); what it buys is
fewer census walks and a 256 MiB large-block cache for workloads
that churn large blocks and never idle. **footprint** releases
earlier and caps the large cache at 8 MiB, which is where the
python/node peak cuts come from; its one disappointment is lua,
whose peak did not move this session (19.1 vs 18.8 MB balanced)
despite the previous worker's paired A/B showing a small
reversal (18.8 vs 19.1 the other way) — the effect, if real, is
smaller than session noise, and ADR 0024's instrumentation item
stays open (§7).

**Guidance:**

- *Default / unsure:* **balanced**. It is the swept optimum and
  the only profile that is never wrong in the table above.
- *Long-running daemons that idle* (the bursty shape),
  *memory-capped containers*, *big managed runtimes* (python,
  node): **footprint** — idle retention and peak both fall, hot
  path unchanged.
- *Batch jobs that churn and exit*, *large-block-heavy servers
  that never idle*: **throughput** is safe to try — release
  policy is irrelevant to a process that exits or never frees,
  and the large cache is 4× deeper. Do not use it where idle RSS
  is billed: it holds what balanced returns.

## 6. The idle-process question (ADR 0029)

Release is activity-driven: a process that frees a working set
and then goes *fully* idle never runs another census, so its dead
spans stay resident indefinitely — bursty only escapes this
because its idle phases carry a replacement-churn trickle. ADR
0029 is the design pass: a timer thread (armed when the first
dead span is marked, disarmed when a census comes back clean) is
the only sound mechanism found — signal-based release is not
async-signal-safe, and glibc has the same limitation (its answer
is the explicit `malloc_trim`, which v2 also honours, ADR 0015).
Decision: **deferred**, with named reopening triggers — a
measured harm case first (a zero-trickle bursty variant is in
the backlog), and an opt-in `FM_IDLE_RELEASE=1` prototype before
any default.

allocators (0 wrk errors + body diff, 0 failed pgbench
transactions, matching ruby/bursty checksums), as did the 8-app
matrix (zero FAILs). Demo updated with the round-5 matrix
(round selector now offers rounds 3–5) and its script
syntax-checked.
