## Measurements

This section belongs to `round8/measurements`, based on current main
**337d7d5** (round 7 merged). Allocator sources, profiles and defaults are
unchanged. ADRs **0037–0039** cover every measurement/design decision below;
0040+ and the separate Timer lifecycle section belong to the sibling task.

### Environment and interpretation

These are **indicative measurements in a shared/noisy cloud container**, not
a quiet-box or reference-VM refresh. Historical round 5–7 numbers are not
baselines for this hardware. The container exposes three Xeon Platinum
8573C CPUs but has a **two-CPU cgroup quota** (`cpu.max=200000 100000`);
throttling and scheduler contention affect multi-thread/process cells.
Timing workloads ran sequentially; the full correctness suite and debug
stress did not overlap them. A short diagnostic compilation/bookkeeping
occurred during the first cache-search series and adds to its noise. No
sample was discarded for that reason. This does not establish exclusive
host ownership. Debian 13, GCC 14.2/O3
allocator builds; exact package versions and CPU details are saved in
`bench/results/round8/environment.txt`.

Every table uses **medians**, never the legacy harness's best run. CV is
sample standard deviation / sample mean, in percent; ranges, sample SDs and sample variances
are retained in `bench/results/round8/summary.json`, alongside every raw
sample in the JSONL files. RSS is KiB (server cells sum process RSS, so
shared mappings are double-counted; this is not PSS). Repetitions measure
host variation, not independent machines. No statistical significance or
universal allocator ranking is claimed. See `bench/round8/README.md` for
commands, fixture generation, instrumentation and reproduction details.
CV is undefined for all-zero error/failed-count columns and is saved as null,
with zero SD/variance; the initial summary divide-by-zero was corrected
without dropping any samples.

Provisioning attempts: the documented sudo/package helper was absent;
the configured Debian snapshot returned HTTP 403. Packages were downloaded
from the allowed Debian trixie repository and unpacked under gitignored
`work/tools`, without a system install. An initial download request named
two unavailable packages; corrected names were used. This gives real
**lua5.4 5.4.7**, Ruby **3.3.8**, nginx **1.26.3**, and PostgreSQL **17**.
The pgbench version differs from round 6's v16, another reason to re-baseline
within this round rather than compare historical absolute numbers.

### Realloc cache search: ADR 0037

Unchanged existing workloads: Lua's `churn.lua`, jq's filter/sort of the
seeded 200k-record JSON fixture, Ruby's `bench.rb` JSON/object churn, and Python 3.12.14's existing
`churn.py` JSON/large-bytes churn.
Each build/app has **one excluded warmup pair plus nine measured pairs**,
off/on order reversed on alternate pairs. Both v2 and JIT use default
profiles, timer off, and differ only in `FM_REALLOC_CACHE_SEARCH=0/1`.
Wall time brackets the target subprocess; wait4 supplies that child's peak
RSS. Checksums/results are Lua **19466078**, jq **66395**, Ruby **32103**, Python **625726** on
every run. The initial script had a wrong jq expected literal; its first
warmup established the fixture's 66395, and the committed driver enforces
that exact result. Raw output is retained for independent checking.

**Per-app verdicts:**

- **Lua: reject adoption.** Median movement is under 1.2%, only 5/9 pairs
  faster in each build, RSS effectively unchanged.
- **Ruby: reject adoption.** Only 5/9 pairs faster; time changes direction
  between v2 (−1.20%) and JIT (+2.90%), with effectively unchanged RSS.
- **Python: adopt the opt-in for this tested workload, provisionally.**
  Medians improve **7.88% v2 / 7.70% JIT**, with **7/9 / 9/9** faster pairs.
  Peak RSS medians fall **10.00%** in both builds (about 49 MiB), with almost
  no RSS variation. This provides a real workload adoption case for the
  existing opt-in, even though wall-time ranges overlap in the noisy host.
  It is a trace-specific recommendation, not a universal Python claim.
- **jq: reject adoption; negative control only.** Its v2 −5.89% median has
  on-CV 16.27%, only 5/9 faster pairs, and just −0.33% on JIT. More
  fundamentally, the counter found **zero non-NULL realloc calls**: this
  build uses other allocation paths. It does **not** satisfy the requested
  realloc-heavy coverage. Python was added after that reachability check;
  Python and Ruby are the two additional realloc-heavy applications.

**Retain global default-off.** Python supports workload-specific opt-in;
Lua/Ruby do not establish a broad benefit, and this noisy cloud run is not
controlled-hardware confirmation. No allocator behavior/default changed.
Python's pymalloc still handles small objects internally; the relevant
libc realloc growth subset is measured, not assumed from Python source.
The separate untimed counts below include startup and never enter timings.

### Central/census ownership: ADR 0038

Same-compiler/O3 round-6 control **f6d5875** versus current round-7 v2.
**One excluded warmup pair plus nine measured alternating pairs per case**.
This prices the ADR 0035 ownership **bundle** (central/census mutexes,
atomic dead marks and thread-local census results), not a pure nanoseconds
per mutex experiment. Timer and wider cache search are off on both builds;
the remaining round-7 timer registration/code-layout differences are a
confound. The historical control contains known C races and is never a
candidate to restore. All recorded runs completed and all new harness
count/endpoint assertions passed; this does not prove that control safe.

The legacy local case is eight threads × 10M alloc/free iterations. Its
cross case is **one producer + one consumer**, 10M transfers, a 4096-slot
ring; the `8` argument does not create eight cross threads. The new
`bench/ownership.c` uses **four producer/consumer pairs (eight threads)**,
200k transfers per pair, 256-slot independent rings, requests
`16 + (i % 128)*256` bytes (16…32528 B, **64 distinct allocator classes**).
Each transfer checks both endpoint bytes and final counts. `census` adds
malloc_trim after every 8192 frees per consumer (96 explicit trims total);
automatic census cadence remains enabled in both cases.

| case | round 6 median s (CV %, range s) | round 7 median s (CV %, range s) | median change | slower pairs |
|---|---:|---:|---:|---:|
| local | 0.460630 (3.58, 0.440162–0.489971) | 0.509261 (2.81, 0.479937–0.526942) | +10.56% | 9/9 |
| cross | 0.241031 (38.62, 0.232763–0.541047) | 0.350998 (27.30, 0.228643–0.503513) | +45.62% | 5/9 |
| many | 2.748416 (57.08, 2.082929–8.191436) | 4.060208 (27.22, 2.578505–6.561205) | +47.73% | 7/9 |
| census | 3.052513 (1.62, 2.963398–3.119114) | 3.931927 (6.10, 3.564349–4.245283) | +28.81% | 9/9 |

The prior “~15% on cross-free” is **not confirmed as a stable estimate**:
this container's ratio of medians is +45.62%, with CVs 38.62%/27.30% and
only 5/9 slower pairs. Many-class traffic is also noisy (control outlier
8.19 s; no outlier discarded), but current is slower in 7/9 pairs. The
census-heavy case is much more consistent: +28.81%, 9/9 slower pairs,
CV 1.62%/6.10%. There is a **real, material contention cost in this shape**;
do not claim neutrality. Local also costs +10.56%; the separate lock diagnostic shows that even
this local churn repeatedly reaches central ownership through periodic
flush/refill, despite lockless individual fast-path operations.

The separate instrumented lock diagnostic below supplies attribution, not
another throughput score. Its two clock reads per acquisition and shared
counter updates perturb scheduling; summed acquisition times overlap
between threads and cannot simply be subtracted from wall time.

Considered epoch/hazard reclamation in response to the material many-class
cost. **Defer; no reclamation prototype was built.** Header lifetime alone
is insufficient: census span metadata still needs exclusive ownership,
and epoch retirement requires thread-exit, stalled-reader and fork rules.
Restoring the known-racy Treiber implementation or merely removing locks
would not be a valid candidate. A separately scoped safe design plus
application-level evidence on controlled hardware is needed before paying
that complexity. Retain ADR 0035's correctness fix unchanged.

#### Honest score and limits

For a conservative descriptive score, overlapping observed time/throughput
ranges count as **tie/unresolved**. Non-overlap gives a provisional win/loss
on this hardware. This is not a significance test; five samples and a shared
host do not establish population rankings. Memory is scored separately.

| cell | v2 time/throughput vs glibc | v2 median change vs glibc | v2 median RSS vs glibc |
|---|---|---:|---:|
| nginx | provisional win | +36.98% | +59.51% |
| pgbench | tie/unresolved | +1.42% | +8.31% |
| ruby | tie/unresolved | -2.38% | +8.28% |

nginx's nearest v2/glibc range endpoints are only 0.64% apart, despite the
large median difference: the descriptive win is fragile, not a 37% universal
speedup claim. nginx's client threads plus two worker processes compete inside a two-CPU
quota; its run spread precludes a universal throughput title. PostgreSQL's
multi-process OLTP includes shared-buffer, database-lock, socket and CPU
contention that this experiment does not isolate from allocator effects.
Do not infer allocator-lock attribution from those app medians. Ruby's
GC/runtime work is substantial too. All raw samples remain visible when
ranges overlap. The reference quiet-box refresh remains **open**; this is
the requested cloud re-baseline, not a claim to have acquired quiet hardware.

Demo cards 07–09 now display these three cells, five-run medians and CVs,
with units and the shared/noisy caveat. Older cards remain labelled history;
no old cell is relabelled as a round-8 measurement.
